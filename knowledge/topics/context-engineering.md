# Context engineering

**Snapshot and source retrieval date:** 2026-11-18; **last synthesis review:** 2026-11-18.
**Evidence status:** Original cross-provider guidance based on reviewed sources in the provider inventories. Context limits and mechanics are model/surface-specific.

## Practical guidance

1. **Optimize for useful signal, not maximum input.** Include the goal, constraints, relevant files, evidence, and success criteria. Retrieve additional context just in time instead of front-loading the entire repository or tool catalog.
2. **Keep context layered and navigable.** Use a concise entry-point instruction, then point to focused topic docs, task artifacts, and references. Load long procedures or examples only when they are relevant.
3. **Give tools bounded, descriptive interfaces.** Tool definitions and results consume context. Use specific schemas and names, return compact relevant results, and keep large intermediate data outside the model context when the runtime permits.
4. **Manage the context lifecycle.** Track what has been decided, what remains, evidence gathered, and the next action. Before compaction or handoff, write durable status to a task artifact; after compaction, verify that critical constraints and unresolved work survived.
5. **Separate context from durable state.** Conversation history is not a reliable database. Persist code changes, test results, decisions, and checkpoints in reviewable files or the host's documented session store.
6. **Handle truncation and recovery explicitly.** Preserve ordering and identifiers required by the provider's API, avoid replaying the same history through two state mechanisms, and verify resumed state instead of assuming a stream or tool call completed.
7. **Load tool definitions just in time when supported.** Large tool catalogs can consume context and increase selection ambiguity; defer infrequently used tools, but account for the extra lookup step and host/model-specific activation rules.
8. **Treat session events, artifacts, and traces as separate records.** Reconnect by retrieving durable state instead of assuming streams replay; store task outputs outside ephemeral execution environments and record enough identifiers to avoid repeating side effects.

## Provider-specific boundaries

- **OpenAI:** Codex instruction limits and discovery rules are product-specific; Responses API compaction and Agents API session/event state are separate mechanisms. Streams do not replay missed session events, so fetch session items and confirm the turn state. Environment lifetimes are independent of sessions, and only selected OpenAI-hosted outputs are published as artifacts; self-hosted results remain the app's responsibility. See [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Compaction](https://developers.openai.com/api/docs/guides/compaction), [Agents API events and items](https://developers.openai.com/api/docs/guides/agents-api/sessions/events), [Environment lifecycle](https://developers.openai.com/api/docs/guides/agents-api/environments/lifecycle), and [Files and artifacts](https://developers.openai.com/api/docs/guides/agents-api/environments/files).
- **Anthropic:** Context-window size does not establish context quality. For Messages API parallel tool calls, the client chooses safe concurrency and must return all results in the prescribed next message, keyed to their tool-use IDs. Tool definitions can be deferred, while memory-tool state is client-side and managed separately from the active conversation. See [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows), [Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents), [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing), [Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use), [Tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), and [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
- **GitHub Copilot:** Conversation context and Copilot Memory are separate; compaction can lose fine detail. Copilot CLI tool search can defer external tool definitions, but its activation threshold and model support are volatile and CLI-specific. The SDK's `clearContext` is a tool-handler-only transition that retains session/event identity while clearing model-facing history; it requires a seed prompt and is unavailable for remote sessions, so it is not session deletion or memory erasure. See [Context management](https://docs.github.com/en/copilot/concepts/prompting-and-context/context-management), [SDK context management](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/context-management), [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory), [Copilot SDK agent loop](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop), and [tool search](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/tool-search).

## Uncertainty and conflicts

The cited docs cover distinct runtime state models; there is no provider-neutral context-window size, compaction format, replay contract, or memory retention policy. Product limits and model capabilities are volatile. Check the current doc for the exact surface in use, and keep an explicit source date when a limit or behavior is important to a design.
