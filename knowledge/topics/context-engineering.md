# Context engineering

**Snapshot and source retrieval date:** 2026-11-18; **last synthesis review:** 2026-11-18.
**Evidence status:** Original cross-provider guidance based on reviewed sources in the provider inventories. Context limits and mechanics are model/surface-specific.

## Practical guidance

1. **Optimize for useful signal, not maximum input.** Include the goal, constraints, relevant files, evidence, and success criteria. Retrieve additional context just in time instead of front-loading the entire repository or tool catalog.
2. **Keep context layered and navigable.** Use a concise entry-point instruction, then point to focused topic docs, task artifacts, and references. Load long procedures or examples only when they are relevant.
3. **Give tools bounded, descriptive interfaces.** Tool definitions and results consume context. Use specific schemas and names, return compact relevant results, and keep large intermediate data outside the model context when the runtime permits.
4. **Manage the context lifecycle.** Track what has been decided, what remains, evidence gathered, and the next action. Before compaction or handoff, write durable status to a task artifact; after compaction, verify that critical constraints and unresolved work survived.
5. **Separate context from durable state.** Conversation history is not a reliable database. Persist code changes, test results, decisions, and checkpoints in reviewable files or the host's documented session store.
6. **Handle truncation and recovery explicitly.** Preserve ordering and identifiers required by the provider's API, avoid replaying the same history through two state mechanisms, and verify resumed state instead of assuming a stream or tool call completed.
7. **Load tool definitions just in time when supported.** Large tool catalogs can consume context and increase selection ambiguity; defer infrequently used tools, but account for the extra lookup step and host/model-specific activation rules.
8. **Treat session events, artifacts, and traces as separate records.** Reconnect by retrieving durable state instead of assuming streams replay; store task outputs outside ephemeral execution environments and record enough identifiers to avoid repeating side effects.

## Provider-specific boundaries

- **OpenAI:** Codex instruction limits and discovery rules are product-specific; Responses API compaction and Agents API session/event state are separate mechanisms. Streams do not replay missed session events, so fetch session items and confirm turn state. Environment lifetimes are independent of sessions, and only selected OpenAI-hosted outputs are published as artifacts; self-hosted results remain the app's responsibility. A Cookbook example separates compaction within a long run from a human-reviewed memo that carries lessons to later runs. See [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Compaction](https://developers.openai.com/api/docs/guides/compaction), [Memory and compaction Cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction), [Agents API events and items](https://developers.openai.com/api/docs/guides/agents-api/sessions/events), [Environment lifecycle](https://developers.openai.com/api/docs/guides/agents-api/environments/lifecycle), and [Files and artifacts](https://developers.openai.com/api/docs/guides/agents-api/environments/files).
- **Anthropic:** Context-window size does not establish context quality. For Messages API parallel tool calls, the client chooses safe concurrency and must return all results in the prescribed next message, keyed to their tool-use IDs. Tool definitions can be deferred, and the tool-context docs distinguish prompt caching, tool search, context editing and programmatic calling as different levers. The compaction docs describe on-demand behavior separately from threshold compaction; the new pages carry version/beta caveats. See [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows), [Context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents), [Manage tool context](https://platform.claude.com/docs/en/agents-and-tools/tool-use/manage-tool-context), [Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing), [Tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), and [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
- **GitHub Copilot:** Conversation context and Copilot Memory are separate; compaction can lose fine detail. Copilot CLI tool search can defer external tool definitions, but its activation threshold and model support are volatile and CLI-specific. The SDK's `clearContext` keeps session/event identity but clears model-facing history, is tool-handler-only, and is unavailable for remote sessions. CLI session history can also be stored locally and synced to the account by default; confirm sync policy before treating a session record as local-only. See [Context management](https://docs.github.com/en/copilot/concepts/prompting-and-context/context-management), [SDK context management](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/context-management), [Session data](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle), [Copilot Dreaming](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-dreaming), [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory), [Copilot SDK agent loop](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop), and [tool search](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/tool-search).

## Uncertainty and conflicts

The cited docs cover distinct runtime state models; there is no provider-neutral context-window size, compaction format, replay contract, or memory retention policy. Product limits and model capabilities are volatile. Check the current doc for the exact surface in use, and keep an explicit source date when a limit or behavior is important to a design.

## Further guidance from the 2026-11-18 review batch

- Keep stable prompt prefixes stable when caching matters: exact-prefix reuse is sensitive to earlier prompt changes. Compaction may reduce reuse, so evaluate cache savings and context reduction as distinct goals ([OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), partial).
- Separate model context from execution state. The OpenAI Agents SDK sandbox guide assigns context, approvals, tracing, and run state to the harness, while files, commands, ports, and snapshots belong to the sandbox ([OpenAI Sandbox Agents](https://developers.openai.com/api/docs/guides/agents/sandboxes), partial). Anthropic likewise states that a Managed Agent session is not the model's context window ([Managed Agents research](https://www.anthropic.com/research/managed-agents), full).
- Delegate only when the task benefits from isolated context. Copilot IDE subagents return a result to the parent rather than sharing the entire conversation; their tool/model behavior depends on the IDE. State a bounded assignment and the required evidence in the handoff ([Copilot IDE subagents](https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/use-copilot-agents/use-subagents), partial).
- Load skills and tool definitions progressively, but inspect the host's discovery rules and limits. Claude Code documents on-demand skill loading and deferred MCP tool search, while Copilot's IDE subagent guide and OpenAI's skill formats describe different surfaces; do not assume one activation or context model ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works), full; [OpenAI Build skills](https://developers.openai.com/plugins/build/skills), partial).
