# Memory engineering and management

**Snapshot and source retrieval date:** 2026-11-18; **last synthesis review:** 2026-11-18.
**Evidence status:** Original cross-provider guidance based on reviewed sources in the provider inventories. Product memory features are not equivalent.

## Practical guidance

1. **Decide what deserves persistence.** Store stable, reusable facts and preferences; keep transient task state in a task artifact, worktree, issue, or session record. Avoid turning every past interaction into a permanent instruction.
2. **Keep memory small, specific, and attributable.** Record the fact, its scope, source, and when it was verified. Prefer a short statement with a path or citation over a broad summary that silently blends inference with evidence.
3. **Separate scopes.** Distinguish user preference, repository convention, organization policy, and task-local progress. Apply the narrowest scope that makes the information useful; do not expose one repository's details as universal user memory.
4. **Treat retrieval as a hypothesis.** Check that a recalled fact still applies to this repo, branch, version, or task before acting. Stale or conflicting memory should be verified against current source-of-truth files and docs.
5. **Make updates reviewable.** Add a memory only when it is durable and useful for future work; revise or retire it when evidence changes. Do not rely on model-generated memory for a safety boundary that must be enforced.
6. **Use compaction and memory for different jobs.** Compaction reduces active conversation history; durable memory preserves selected facts across sessions. A compacted summary is not a permanent source of truth, and a memory store is not necessarily a verbatim transcript.
7. **Make storage and update policy explicit.** Clarify who writes memory, which namespace they can access, how it is retained, and what process checks stale or contradictory notes. A client memory tool's filesystem semantics are not equivalent to a vendor-managed persistent-memory feature.

## Provider-specific boundaries

- **OpenAI:** Codex memory is a distinct product feature and is off by default in the reviewed docs; required project rules belong in checked-in instructions. Responses API compaction is separate from persistent Codex memory. A Cookbook example uses a human-reviewed memo as workflow memory across runs, while compaction sustains one long run; treat the notebook as an illustrative pattern, not product behavior. Follow each surface's state/replay rules. See [Codex memories](https://learn.chatgpt.com/docs/customization/memories), [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Compaction](https://developers.openai.com/api/docs/guides/compaction), and [Memory and compaction Cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction).
- **Anthropic:** Claude Code auto memory and `CLAUDE.md`/rules have separate roles; memory is context, not a permission boundary. The Messages API memory tool is client-managed file storage under a `/memories` namespace, so the application owns persistence, retention, and path validation. Managed Agents offers a separate beta workspace-mounted memory store with immutable revisions; do not assume storage or scope is portable between these products. A separate research article describes an experimental "dreaming" pass that checks and organizes notes against transcripts; its benchmark figures are study-specific, not a product guarantee. See [Claude Code memory](https://code.claude.com/docs/en/memory), [Claude Code security](https://code.claude.com/docs/en/security), [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory), [Components of agent memory](https://www.anthropic.com/research/components-of-agent-memory), and [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing).
- **GitHub Copilot:** Copilot Memory distinguishes repository-scoped facts from user preferences and is governed by eligibility/policy controls. Copilot Dreaming is documented as a public-preview feature that can update memory automatically; checked-in instructions and skill updates instead require a pull request that a person merges. Treat the boundaries as current docs/preview claims, not a universal retention contract. The Copilot Memory hub reviewed in a separate batch is only an index; its linked admin/how-to pages remain unread. A dated engineering blog describes a distinct citation-based memory design and should not be generalized beyond the post's account. See [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory), [Copilot Dreaming](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-dreaming), [Memory hub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory), [Context management](https://docs.github.com/en/copilot/concepts/prompting-and-context/context-management), [Agentic memory post](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/), and [Agentic engineering](https://github.blog/ai-and-ml/github-copilot/beyond-code-generation-a-developers-guide-to-agentic-engineering/).

## Uncertainty and conflicts

“Memory” may mean a product-managed recall store, checked-in instructions, conversation state, or an external database. Those mechanisms have different retention, scope, retrieval, and deletion behavior. Do not assume one vendor's memory feature is enabled, shared, or available in another provider's surface; verify current product docs and policy. This is a snapshot, not a claim about a user's account settings.

## Further guidance from the 2026-11-18 review batch

- Keep in-run compaction separate from cross-run memory. A reviewed memo can preserve workflow lessons across sessions; compaction only reshapes active history. Preserve a human-reviewed source of truth and record when its assumptions were verified ([OpenAI memory and compaction example](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction), partial).
- Make memory ownership and scope explicit. Copilot's manual-memory guide says a model decides whether to store a request; repository facts require the relevant feature and write access, CLI subagents cannot write/vote, and writes may require approval. Its dated changelog says a repository off switch stops new storage and reading but does not delete already stored facts; deletion is a separate lifecycle action ([Copilot memory creation](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory/create-memories), partial; [May 2026 memory controls](https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli), full).
- Treat checkpoints as narrow rollback aids, not complete memory restoration. Claude Code documents checkpoints for its own file edits, while local session JSONL and project instructions serve different purposes; shell actions and user edits need separate version-control protection ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works), full; [Claude Code autonomy announcement](https://www.anthropic.com/news/enabling-claude-code-to-work-more-autonomously), full).
