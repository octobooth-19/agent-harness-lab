# Prompt engineering for agents

**Snapshot and source retrieval date:** 2026-11-18; **last synthesis review:** 2026-11-18.
**Evidence status:** Original cross-provider guidance based on reviewed sources in the provider inventories. Product-specific behavior is not portable by default.

## Practical guidance

1. **Write for a task, not a persona alone.** State the goal, relevant repository or environment, constraints, observable acceptance criteria, and expected handoff. Keep role text short unless it changes the agent's decisions.
2. **Separate durable project rules from task instructions.** Put stable conventions and constraints in the host's supported project-instruction mechanism; keep one-off goals in the task prompt. Link to focused references rather than copying a whole manual into every prompt.
3. **Make instructions operational.** Prefer “run the focused test, inspect the diff, and report any failure” over “be careful.” State what must not happen, which tools or files are in scope, and how to handle uncertainty or a blocked prerequisite.
4. **Use progressive disclosure for reusable procedures.** A skill should have a concise routing description and a focused procedure; load detailed references or scripts only when needed. Test both correct activation and non-activation. A skill describes a workflow but does not itself grant tools or permissions.
5. **Treat natural-language guidance as probabilistic.** If an outcome must be guaranteed, enforce it with the host's permissions, deterministic checks, hooks, tests, or review gates instead of relying on prompt wording.
6. **Version and evaluate prompt changes.** Use representative tasks, an explicit rubric or measurable checks, and repeated trials for nondeterministic behavior. Evaluate the full model-plus-harness workflow, not just whether the final prose sounds plausible.
7. **Constrain instruction and data flow.** Keep untrusted external input out of privileged instruction channels; where a workflow passes model output between steps, prefer schema-constrained fields to free-form text. Add review gates for sensitive tool calls rather than assuming a prompt can prevent every misuse.
8. **Describe tools from the caller's perspective.** Explain purpose, when not to use the tool, parameter semantics, limitations, and response shape. For complex schemas, include valid examples and return only the information needed for the next decision.
9. **State a safe completion contract.** Define what done means, which checks to run, and which actions may proceed without a new approval. Keep required security invariants in deterministic policy/CI; tune model-specific style or verbosity only after representative evaluation.

## Provider-specific boundaries

- **OpenAI:** Codex `AGENTS.md` discovery and precedence are product-specific; its skill formats and API/plugin-attached skills also differ by surface. Codex local custom prompt files are deprecated in favor of skills, while its rules files are experimental policy rather than model instructions. Agents SDK applications own their own review and guardrail behavior; Codex product controls do not automatically transfer. The reviewed Agent Builder safety page warns against placing untrusted values in developer messages and recommends structured outputs, input guardrails, and tool approvals. A personalization Cookbook example also warns that selected memory injected into the prompt is sent to the model API; minimize and scope that content. Agent Builder is scheduled to shut down Nov. 30, 2026, so treat these as design patterns, not a reason to adopt the retiring product. See [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Build skills](https://learn.chatgpt.com/docs/build-skills), [Codex rules](https://learn.chatgpt.com/docs/agent-configuration/rules), [Custom Prompts](https://learn.chatgpt.com/docs/custom-prompts), [Plugin Skills](https://developers.openai.com/plugins/concepts/skills), [SDK guardrails and approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals), [Agent Builder safety](https://developers.openai.com/api/docs/guides/agent-builder-safety), and [Context Engineering for Personalization](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization) (partial).
- **Anthropic:** `CLAUDE.md`, rules, skills, hooks, and Agent SDK options belong to Claude Code/SDK semantics. Prompts and project memory influence the model; the documented permission/hook layer supplies enforcement. For Messages API tools, Anthropic emphasizes detailed descriptions, schema/examples, and high-signal results. Its authoring guide recommends concise skills and matching instruction rigidity to task fragility; this is product guidance, not a universal token rule. See [Claude Code best practices](https://code.claude.com/docs/en/best-practices), [skills](https://code.claude.com/docs/en/skills), [skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [permissions](https://code.claude.com/docs/en/permissions), and [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools).
- **GitHub Copilot:** Instructions, custom agents, skills, and MCP support vary by surface and host. The CLI's listed instruction files do not have a documented precedence order, and edits require restarting/resuming a session; keep overlapping guidance consistent and verify the target host's behavior. Prompt files are invocation templates, not automatically applied custom instructions. Hooks can act at runtime but their supported events vary by host and preview status. The CLI MCP guide's per-server tool selection defaults to `*`, so narrow it explicitly when least privilege is intended; this is tool configuration, not something a prompt alone can enforce. See [custom instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions), [CLI instruction loading](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions), [prompt files](https://docs.github.com/en/copilot/concepts/prompting-and-context/prompt-files), [hooks](https://docs.github.com/en/copilot/concepts/customizations/hooks), [custom agents](https://docs.github.com/en/copilot/concepts/customizations/custom-agents), [CLI MCP configuration](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers) (partial), and [agent skills](https://docs.github.com/en/copilot/concepts/customizations/agent-skills).

## Uncertainty and conflicts

“Prompt” can refer to user task text, persistent instructions, skill procedures, agent profiles, or messages sent through an API; these are distinct configuration layers. The three providers document different discovery, precedence, inheritance, and execution rules, so do not transplant a file name or frontmatter field between hosts without checking the current target docs. The cited material was accessed on the snapshot date; model and product behavior may have changed since then.

## Further guidance from the 2026-11-18 review batch

- When defining a multi-agent system, start with one focused agent and separate roles only when tool access, ownership, or approval needs differ. Make the task prompt state expected outcomes and verification rather than relying on a broad persona ([OpenAI agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents), partial).
- Treat tool descriptions as part of prompt design: specify purpose, when not to use the tool, parameter meaning, limitations, and the response shape needed for the next decision. Consolidate only when it reduces selection ambiguity; do not make a single tool an unbounded catch-all ([Anthropic tool definition guidance](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), full).
- For custom agents, explicitly set allowed tools instead of assuming omission is restrictive. Copilot documents that an unset `tools` field defaults to all tools; its IDE and CLI fields are not interchangeable. The configuration page was partial, so recheck current schema details before adopting limits ([Copilot custom-agent configuration](https://docs.github.com/en/copilot/reference/custom-agents-configuration), partial).
- Keep `AGENTS.md` task-ready: name the repository stack, provide executable test/build commands, explain structure and workflow, and mark boundaries explicitly. The cited GitHub post summarizes a sample of repositories and was only partially read, so treat its pattern as author guidance, not a measured universal rule ([GitHub AGENTS.md study](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/), partial).
- Choose the smallest supported customization that fits: use persistent instructions for conventions, skills for reusable task procedures, and hooks for deterministic runtime actions. Keep project context and available tools clear, but do not describe instructions as enforceable requirements; use permission checks for that ([Copilot customization comparison](https://docs.github.com/en/copilot/concepts/customizations/comparing-customizations), full; [custom-instructions tips](https://github.blog/ai-and-ml/github-copilot/5-tips-for-writing-better-custom-instructions-for-copilot/), full).
- Select the model independently from the prompt and evaluate it against representative work. Keep model/provider defaults explicit when transport or SDK features differ; avoid prescribing one vendor's current default as a universal choice ([OpenAI Agents SDK model selection](https://developers.openai.com/api/docs/guides/agents/models), partial).
- Treat skills as versioned procedures, not just prompt text: have someone other than the author review them, test with representative queries, and pin the version deployed in production. Skill discovery and sharing differ across Claude API, Claude.ai and Claude Code ([Anthropic skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise), full).
- Match the prompt/tool contract to the execution surface. A desktop-computer-use agent, a structured tool caller, and an API harness with an external sandbox have different observable actions and authority; state the permitted surface and verification expectations instead of assuming a prompt makes them equivalent ([Copilot computer use](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/computer-use), full; [Anthropic browser-use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool), partial; [OpenAI AWS sandbox guide](https://developers.openai.com/api/docs/guides/agents-api/environments/providers/aws), full).
- For an unattended action, put a bounded task and review contract in the prompt, but verify the host's trigger, permission, and billing rules separately. In particular, the Copilot CLI-in-Actions guide documents fork-trigger and cost considerations, while OpenAI's hosted Agents API plugins have environment-specific behavior and do not retroactively reload into existing sessions ([Copilot CLI in GitHub Actions](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/copilot-cli-in-github-actions), full; [OpenAI Agents API Plugins](https://developers.openai.com/api/docs/guides/agents-api/tools/plugins), full).
- For work launched via MCP, write a bounded outcome and verification contract, then rely on the host's actual policy and review path. A Copilot cloud-agent MCP request produces a draft PR for review, while Copilot CLI MCP configuration can expose all tools by default unless narrowed ([Using Copilot cloud agent via the GitHub MCP Server](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-with-mcp), full; [Adding MCP servers for GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers), partial).
- Name the actual tool set and execution boundary in the task contract: Copilot's GitHub MCP toolsets can be configured selectively, while OpenAI programmatic tool code runs in a restricted V8 runtime and is not the recommended default for approval-sensitive writes. Keep prompt expectations aligned with what the host exposes, then enforce permissions outside the prompt ([GitHub MCP toolsets](https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/customize-copilot/extend-copilot-with-tools-and-context/configure-toolsets), full; [OpenAI Programmatic Tool Calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling), partial).
- Pin the production model where the API supports snapshots, and rerun prompt tests/evaluations when changing model versions. Treat generated prompts as drafts. For OpenAI API prompt objects, follow the dated migration notice and move content into reviewed, version-controlled code with typed inputs; check the current deprecation timeline before relying on its shutdown date ([OpenAI prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), partial; [Prompt generation](https://developers.openai.com/api/docs/guides/prompt-generation), partial; [Prompt-object migration](https://developers.openai.com/api/docs/guides/prompting/migrate-from-prompt-object), partial).
- For GPT-5.6-family tasks, try an outcome-first prompt: retain the goal, evidence, constraints, success criteria, and stop conditions, and remove redundant rules/tools one group at a time while rerunning the same evals. The advice and reported gains are model/workload-specific, so do not generalize them into a universal “shorter is better” rule ([GPT-5.6 Sol prompting guidance](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6), partial).
- For parallel CLI work, prompt with concrete artifacts, separate file/module ownership, explicit dependencies, and per-task validation; a Fleet orchestrator can run independent work concurrently but agents share a filesystem and do not communicate directly. Treat this as a dated Copilot CLI feature description, not a provider-neutral multi-agent contract ([Copilot CLI `/fleet`](https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/), partial).
- Make agent completion criteria independently gradeable. Anthropic's Managed Agents outcome feature asks for a per-criterion rubric and sends a separate-context grader's feedback into an iteration loop; verify the artifact and retain external checks rather than treating grader feedback as proof of correctness ([Define outcomes](https://platform.claude.com/docs/en/managed-agents/define-outcomes), partial).
- Distinguish a scheduled prompt from a durable automation in its task instructions: Copilot CLI `/every` and `/after` are experimental, session-scoped, and only run while the interactive session is open. An unattended schedule needs a supported external host with explicit trigger, write-scope, approval, and cost rules ([Scheduling prompts in GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/schedule-prompts), partial; [Copilot Automation controls](https://github.blog/changelog/2026-10-28-new-tools-triggers-and-cost-controls-for-copilot-automations), full).
- Treat model-authored starter prompts as model-specific starting points. OpenAI's GPT-5.3-Codex and GPT-5.5 frontend guidance are tied to different model snapshots and tasks; borrow a pattern only after testing it against the target runtime, UX, tools, and representative eval cases ([GPT-5.3-Codex guidance](https://developers.openai.com/api/docs/guides/latest-model/gpt-5.3-codex), partial; [Frontend prompt instructions](https://developers.openai.com/api/docs/guides/frontend-prompt), partial).
- For delegated or voice-driven tasks, evaluate task completion at the artifact and tool-state boundary, not by whether the prompt or assistant response sounds complete. The GPT-Live cookbook follows intent through delegation, executed tools, application state, and final confirmation; this is a useful evaluation pattern, not a result guarantee for other voice products ([GPT-Live evaluation guide](https://developers.openai.com/cookbook/examples/audio/voice_agent_evaluation), partial).
- For Codex tasks, name the review criteria and what counts as finished; choose reasoning effort for the depth of investigation and delegate only work that splits cleanly. The GPT-6.2 guidance is model-specific, so validate the prompt and evaluation on the actual model/runtime ([Prompting GPT-6.2 in Codex](https://learn.chatgpt.com/guides/prompting-gpt-6-2-astra), partial).
- Keep optional repository instructions distinct from task plans and generated phase context. The Codex cookbook's `AGENTS.md`, goals, plans, prompts, and review artifacts are suggested conventions, not required filenames or automatic enforcement ([Iterating development workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex), partial).
- Make review actions explicit: Copilot CLI `/review` can be narrowed to paths or patterns, and the user decides whether a proposed inspection command may run. Treat findings as advice to verify and apply rather than an implicit worktree edit ([Copilot CLI code review](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/agentic-code-review), full).
- Evaluate prompts on task-representative examples with a named objective, grader, and limitations. OpenAI's LifeVal is a curated personal-assistant benchmark rather than a coding-agent proxy, while Anthropic cautions that benchmark results can shift with data exposure, formatting, and implementation choices ([LifeVal](https://openai.com/index/lifeval/), partial; [Evaluating AI systems](https://www.anthropic.com/research/evaluating-ai-systems), partial).
