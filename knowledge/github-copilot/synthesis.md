# GitHub Copilot: knowledge snapshot

**Snapshot date:** 2026-11-18. This is an original synthesis of official GitHub documentation, changelog entries, and blog posts. Product documentation is treated as the current behavior baseline; changelog entries and blog posts are dated evidence of releases, experiments, and advice, not timeless specifications.

## System model

GitHub describes an agent as a system that pursues a goal by planning, using tools, inspecting results, and adapting. The same product family spans collaborative local work, asynchronous cloud work, and trigger-based automation, but the available environment, tools, permissions, and review path depend on the surface. The [agent overview](https://docs.github.com/en/copilot/concepts/agent-capabilities/about-agents/about-github-copilot-agents) distinguishes chat, agents, and automation; it is a better conceptual starting point than treating every Copilot experience as one interchangeable agent.

The [Copilot SDK agent-loop guide](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop) makes one runtime boundary explicit: the SDK transports prompts and events over JSON-RPC, while Copilot CLI orchestrates the tool-use loop. The CLI sends accumulated conversation history to the model, executes requested tools, and continues until the model responds without another tool request. In that guide, one turn corresponds to one model call; `session.idle` is the reliable signal that processing stopped, while `session.task_complete` is a best-effort semantic claim. This is useful instrumentation guidance for SDK integrations, but should not be generalized into undocumented internals of every Copilot surface.

The surfaces are related, not identical:

* **CLI:** interactive and programmatic entry points; local execution is the default, with optional cloud sessions and local sandboxing. Its command and programmatic references expose tool, path, and URL permissions; automatic approval options materially widen access, so they should not be confused with a safer sandbox. See the [CLI overview](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-cli), [command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), and [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference).
* **Copilot app:** a desktop UI built on Copilot CLI, with parallel workspaces, GitHub workflows, and local or cloud sessions. Its [product guide](https://docs.github.com/en/copilot/concepts/copilot-surfaces/github-copilot-app) describes dedicated branches/worktrees and session modes, but this does not imply every other surface has the same UI or execution model.
* **IDE agent mode:** collaborative work in an IDE; available capabilities and customization behavior vary by IDE and version.
* **GitHub cloud agent:** asynchronous repository work that returns a reviewable change, commonly through a pull request. The [responsible-use card](https://docs.github.com/en/copilot/responsible-use/agents) documents distinct data flows and boundaries for cloud agent, Copilot Cloud, CLI, SDK, code review, and the app.

There are at least two distinct hosted execution choices. A **cloud sandbox** is a GitHub-hosted isolated Linux environment and supports continuity across clients; an **Actions** environment uses GitHub Actions runners and supports setup workflows, self-hosted or larger runners, and Windows. The [cloud sandbox guide](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-sandboxes) says to choose the environment at session start. The `copilot-setup-steps.yml` configuration documented [here](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment) applies to Actions sessions, not cloud sandboxes. A historical 2025 [coding-agent onboarding post](https://github.blog/ai-and-ml/github-copilot/onboarding-your-ai-peer-programmer-setting-up-github-copilot-coding-agent-for-success/) explains an earlier issue-to-PR flow centered on Actions; retain its setup advice as dated context, not as the present universal runtime description.

## Customization and control plane

Copilot customizations solve different problems and should be composed deliberately rather than collapsed into a single “prompt” mechanism:

* **Instructions** give persistent guidance about the project, standards, or response style. Repository-wide, path-specific, personal, and organization instructions have surface-dependent availability and precedence. The [custom-instructions guide](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions) explicitly warns that support and ordering vary, and that following instructions is not deterministic.
* **Custom agents** define reusable specialist roles, instructions, and tool restrictions. A profile is a role definition; a subagent is an execution delegated into a separate context. The [custom-agent reference](https://docs.github.com/en/copilot/concepts/customizations/custom-agents) notes that profile properties and instruction inheritance differ by environment.
* **Skills** package task-specific instructions, scripts, and resources for repeatable workflows. They can be shared across supported hosts, but the [skills documentation](https://docs.github.com/en/copilot/concepts/customizations/agent-skills) and GitHub’s [cross-agent skills guide](https://github.blog/ai-and-ml/github-copilot/build-once-run-on-any-agent-a-practical-guide-to-agent-skills/) make the boundary clear: a skill does not itself grant a tool, credential, or permission. Host context and execution remain host-specific.
* **MCP** adds external tools and data. Configuration and support differ between CLI, IDEs, the app, cloud agent, and code review. For cloud agent and code review, repository-level configuration enables tools (not server resources/prompts), and GitHub warns that configured tools can be used autonomously without a separate approval prompt. The [MCP overview](https://docs.github.com/en/copilot/concepts/customizations/mcp) and [repository configuration guide](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers) recommend least privilege, including allowlisting only needed, preferably read-only tools.
* **Hooks and plugins/extensions** add executable lifecycle behavior or package related customizations. For deterministic sequence, checks, conditions, and handoffs, **dynamic workflows** are a closer fit than relying on a prompt to recreate a process.

Prompt files and custom instructions should also remain distinct: the reviewed `.prompt.md` guide presents reusable templates invoked for an interaction, rather than automatically injected repository guidance. Hooks execute configured commands at runtime lifecycle points and can approve or deny `preToolUse` calls, while instructions only ask the model to behave a certain way. Event support varies by host; the cloud agent supports a subset, and VS Code hooks are documented as public preview. Validate the specific host's hook schema and event support before using hooks as a required gate ([Prompt files](https://docs.github.com/en/copilot/concepts/prompting-and-context/prompt-files), [Hooks](https://docs.github.com/en/copilot/concepts/customizations/hooks)).

The [delegation guide](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/delegating-and-parallelizing-work-with-agents) frames parallel work as decomposition, dependency identification, scoped assignment, parallel execution of independent tasks, then review and integration. Its tradeoff is additional model usage and coordination. **Autopilot** is a mode of greater agent autonomy; **fleet** delegates work with task decomposition chosen for that run; a **dynamic workflow** is a program whose author defines steps, conditions, and handoffs. Dynamic workflows can mix deterministic operations and agents, use parallel or sequential stages, and add checkpoints. Their documentation currently labels the feature public preview. See [dynamic workflows](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/dynamic-workflows).

The Autopilot guide narrows when unattended multi-step execution is appropriate: use it for tasks with a clear outcome and enough detail to act; interactive mode better fits exploration, while Plan mode lets a person review an approach before execution. Autonomy and permission settings are explicitly separate; Autopilot does not itself grant unrestricted access, and the user remains responsible for reviewing results before commit or merge. This guidance is documented for the Copilot app and CLI, not every Copilot surface ([Autopilot](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/autopilot)).

The CLI reference further separates **continuation**, **permission**, and **clarification** controls: Autopilot determines whether the agent continues, `--allow-all`/`--yolo` changes approval behavior, and `--no-ask-user` suppresses clarifying questions. These flags are not interchangeable safety settings. Continuation and AI-credit limits bound a run; manual approval mode can auto-deny requests that require approval. `/plan --mode autopilot` can proceed to execution without a separate plan approval, so use a reviewed plan mode when a human decision is required ([CLI Autopilot mode](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/use-autopilot-mode)).

GitHub documents two different automation mechanisms. **Copilot Automations** run a cloud agent on a schedule, repository event, or API trigger and define prompts, triggers, tools, and optional usage limits; the documentation says automation definitions are stored outside Git. **GitHub Agentic Workflows** are repository Markdown/YAML inputs compiled to Actions workflows and are read-only by default, with writes mediated through declared safe outputs and threat detection. Their trust model and repository ownership differ. Do not imply that a Copilot Automation definition is itself a repo file or that Agentic Workflows share the same trigger/policy model ([About Automations](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automations), [About GitHub Agentic Workflows](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows)).

CLI instruction loading is also host-specific: the reviewed guide lists `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, path-scoped `*.instructions.md` and user-level files. It does not define a precedence order among those sources, so avoid contradictory rules; file edits become active after a session restart/resume. A page titled Copilot Memory in this batch is only a navigation hub; its links to personal, repository, organization, and enterprise memory management were not read, so this batch adds no new mechanism claims about those scopes ([CLI custom instructions](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions), [Copilot Memory hub](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory)).

Enterprise governance can constrain where custom-agent definitions are managed: the reviewed guide places enterprise profiles in a `.github-private` repository and describes rulesets for owner-only changes. MCP has a separate enterprise policy to enable/disable servers and allowlist them through managed settings; a custom registry is public preview and has weaker matching. A `readOnlyHint` or an approval rationale is not enforcement—permissions and policy must gate the actual action ([Prepare custom agents](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/prepare-for-custom-agents), [MCP management](https://docs.github.com/en/copilot/concepts/enterprise/mcp-management)).

Context is both conversation and working state: messages, system instructions, tool definitions, tool calls, and results consume the model’s context window. The [context guide](https://docs.github.com/en/copilot/concepts/prompting-and-context/context-management) describes monitoring and compaction, and stresses that summarization can lose fine detail. On Copilot CLI, tool search can defer external tool definitions until needed, reducing upfront context; the current guide describes a roughly 30-tool activation threshold, model compatibility requirements, and `deferTools` controls. Those thresholds and supported models are version-sensitive and should be checked live before use ([tool search](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/tool-search)). [Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) is a separate persistence mechanism: repository facts are scoped to a repository and can be shared, while user preferences follow the user; both have eligibility and policy controls. Neither memory nor context should be treated as a substitute for project instructions or verified source.

The Copilot SDK provides a tool-handler-only `session.history.clearContext` operation that keeps session identity and event/configuration state while clearing the model-facing conversation; it requires a non-empty seed prompt and is rejected for remote sessions. Marking the clearing tool terminal is recommended so the current turn ends cleanly. This is a targeted SDK context transition, not general session deletion or a memory reset ([SDK context management](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/context-management)). Remote control is another separate mechanism: commands are polled from GitHub.com/Mobile while the CLI continues executing locally, and it applies only to interactive sessions; session synchronization is policy-gated and first-response-wins ([Remote control](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-remote-control)).

Copilot Dreaming is documented as a public-preview background process that can curate memory and repository guidance. The current docs distinguish auto-updated memories from checked-in instruction/skill files, which are proposed through a pull request that a person must merge. Eligibility, session-sync prerequisites, and model policy apply; this should not be treated as an always-on or deterministic memory update. A 2026 GitHub Blog post describes a separate agentic-memory design with code citations and just-in-time verification, but it is a dated product account and was only partially reviewed in this snapshot ([Copilot Dreaming](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-dreaming), [Agentic memory post](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)).

CLI tools have two control planes: `--available-tools`/`--excluded-tools` limit which tools are exposed, while `--allow-tool`/`--deny-tool` govern permission; deny takes precedence. Saved approvals and skill `allowed-tools` settings can pre-authorize operations, so avoid broad shell pre-approval for untrusted skills. The CLI's session-data guide describes local history syncing to the account by default and a `chronicle` command that can search sessions or suggest instruction improvements; session sync and policy have privacy implications ([Allowing and denying tool use](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools), [Adding CLI skills](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills), [Session data](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)).

## Execution safety and review

Treat permissions as part of the harness, not as properties conferred by a model, skill, or workflow description. In the CLI, automatic approvals can allow broad tool, path, or URL access. Local sandboxing is separate from cloud sandboxing: the [filesystem policy reference](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/understanding-local-sandboxing) describes deny-by-default path rules, operating-system enforcement for sandboxed child processes, and software checks for built-in file operations. Remote MCP servers are outside the local process sandbox.

Cloud agent has a different boundary. GitHub’s [risk and mitigation guide](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) describes a restricted network firewall, limited branch-writing capability, signed and attributable commits, session logs, security checks, and human review before merge. These are product mitigations, not proof that generated changes are safe. Continue to inspect changes and test them. The 2026 blog post [“The harness is all you need (mostly)”](https://github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly/) advocates broad autonomy as personal workflow advice; its recommendation to use “Allow All” should not override the more specific permission, sandbox, and enterprise controls in current product documentation.

For Copilot Automations, event triggers from users without repository write access are ignored as an injection mitigation; least-privilege tool selection and extra approval for shared-automation pull requests are documented safeguards. These defaults do not make an automation a security boundary: sessions can be visible to repository readers, while issue-triage rationale/approval modes are explicitly not server-enforced controls. Use repository permissions to enforce access, and review the exact automation's tool/trigger configuration ([About Automations](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automations), [Rationale and approvals](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automation-rationale-and-approvals)).

Enterprise settings add a separate kill switch: administrators can block the cloud agent and Copilot code review across owned repositories, including for some users with personal plans. Enterprise monitoring surfaces session activity and audit logs; streaming to Microsoft Agent 365 is a dated public-preview/Enterprise offering. Registry policy is separate from defining a server: current docs recommend managed-settings allowlists over the public-preview custom registry ([Blocking agentic features](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/block-agentic-features), [Monitoring agentic activity](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/monitor-agentic-activity), [MCP registry](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-registry), [Agent 365 changelog](https://github.blog/changelog/2026-11-17-monitor-github-copilot-activity-through-microsoft-agent-365)).

Copilot code review is itself agentic: current docs describe repository context gathering, review-effort levels, and follow-on suggestions. The [code review guide](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/code-review) notes separate AI-credit and Actions-minute cost components for agentic capabilities. The November 17, 2026 [release note](https://github.blog/changelog/2026-11-17-copilot-code-review-adaptive-effort-secret-detection-and-more) adds Adaptive effort, public-preview cross-repository context and secret detection, and code review for Azure DevOps reaching GA. Treat those statuses and availability as dated release claims; verify current policy, plan, and configuration before relying on them.

## Evaluation: model, harness, and task

Model quality alone does not determine agent performance: the harness shapes context, tool access, delegation, retries, and cost. GitHub’s June 25, 2026 [harness evaluation post](https://github.blog/ai-and-ml/github-copilot/evaluating-performance-and-efficiency-of-the-github-copilot-agentic-harness-across-models-and-tasks/) reports comparisons across several coding and terminal benchmarks and describes controlling for model, task, reasoning effort, tools, and MCP configuration. These are GitHub-reported experimental results, not guarantees for a different task or setup.

Two November 17 announcements add complementary evaluation surfaces:

* [GitHub Copilot Evals](https://github.blog/changelog/2026-11-17-github-copilot-evals-is-now-in-public-preview) is a public-preview workflow for repeatable checks of skills, custom agents, and MCP tools. The announcement describes task-plus-criteria evaluations, reviewing failures, and comparing runs before and after a customization change. It identifies Vally as the evaluation engine. The linked Evals documentation and implementation are not covered by this Copilot Docs/blog/changelog inventory.
* The [Copilot benchmarks harness view](https://github.blog/changelog/2026-11-17-github-copilot-benchmarks-site-adds-harness-comparisons) compares harnesses only for matched models at medium reasoning effort and reports resolution and task cost with run variation. Its explicit exclusion of unmatched and Copilot-only configurations is an important comparability constraint.

[ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/), introduced October 5, 2026, is a separate code-review benchmark. Its post describes representative pull requests, multi-source candidate findings, an adjudicated golden set, and grounded/augmented precision and recall. Do not conflate this benchmark with Copilot Evals (customization regression tests) or with the broader harness/model benchmark comparisons.

For reusable evaluation, specify a realistic task, observable acceptance criteria, environment and permission constraints, and relevant cost/latency measures. Keep the model and harness fixed when isolating a change; compare matched configurations; use repeated runs for nondeterministic behavior; and pair offline tests with human review or production-aligned checks where appropriate. Those are synthesis recommendations based on the documented eval and benchmark designs, not additional Copilot product guarantees.
