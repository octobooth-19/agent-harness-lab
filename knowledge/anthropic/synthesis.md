# Anthropic / Claude: coding-agent knowledge snapshot

**Snapshot date:** 2026-11-18
**Scope:** Official Anthropic documentation, Claude Code documentation, product/API release notes, and Anthropic research/news relevant to coding agents and the broader agent platform. This is a useful partial snapshot, not an exhaustive reading of the indexed corpus. See [coverage and limitations](coverage.md) and the [source inventory](source-inventory.csv).

## Executive synthesis

Anthropic’s materials describe several distinct ways to build an agent, rather than one interchangeable “Claude agent” product:

- **Claude Code** is an interactive coding-agent harness with a built-in agent loop, filesystem and shell tools, configurable permissions, hooks, skills, subagents, MCP, and multiple front ends. Its current documentation is at [code.claude.com/docs](https://code.claude.com/docs/en/overview).
- **Claude Agent SDK** embeds the Claude Code loop and tools in a Python or TypeScript application that the developer operates. It exposes the loop’s messages, tools, permissions, sessions, hooks, subagents, MCP, skills, plugins, and related configuration ([SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [agent-loop guide](https://code.claude.com/docs/en/agent-sdk/agent-loop)).
- **Messages API with client tools** leaves the application to implement the tool loop and execution. Claude emits `tool_use`; the client runs the operation and sends back `tool_result`. Anthropic also provides server-side tools and a tool runner ([tool-use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)).
- **Claude Managed Agents** is a hosted, configurable harness with sessions, environments, event streaming, built-in tools, persistence, and optional self-hosted deployment. The API docs mark it beta in this snapshot ([overview](https://platform.claude.com/docs/en/managed-agents/overview)).

These are different control and hosting boundaries. Product capabilities, lifecycle semantics, API beta status, data retention and supported models should be checked against the relevant current product documentation—not inferred from another surface’s documentation or an older blog post.

## Agent-loop and harness design

The Agent SDK documentation describes the basic loop as: provide a prompt plus system context, tools, and history; have the model respond with text and/or tool requests; execute requested tools and feed results back; repeat until there are no tool calls; then return the result and usage/session metadata. The SDK can cap turns and budget, and its result stream distinguishes successful completion from limit/error outcomes ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)).

The current Messages API guides sharpen the protocol contract: client tools require one matching `tool_result` per `tool_use`, placed before any text in the next user message; failed or deliberately skipped calls should return an error result with useful feedback. Treat tool results as untrusted input, not as instructions to promote into a system/developer prompt. The API's Tool Runner automates the loop and result bookkeeping, but is marked beta; keep a manual loop where application-owned approval, logging, or conditional execution is required ([How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works), [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls), [Tool Runner](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-runner)).

Managed Agents adds hosted session controls that do not map directly to the Messages API loop. Its permission policies can run, ask, or evaluate calls automatically; the reviewed guide says `auto` policy intent is derived from user messages, not untrusted tool results or retrieved pages. Session budgets cap model, search, and runtime spend but enforcement occurs between model requests, so the active request may cross the threshold. These are beta product semantics and should be checked against the live API contract ([Permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies), [Budgets](https://platform.claude.com/docs/en/managed-agents/budgets)).

Tool input can be constrained with strict schema handling. Tool search supports deferred loading so only relevant definitions need enter context; SDK custom MCP tools may be deferred by default. These mechanisms reduce invalid input or context overhead, but availability and limitations vary by tool type and API surface. For example, the reviewed docs say browser/computer toolsets do not accept `strict`, and tool annotations such as `readOnlyHint` are not enforcement ([Strict tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use), [Tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [SDK custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools)).

Anthropic’s architecture guidance recommends starting with the simplest adequate system. Its [Building effective agents](https://www.anthropic.com/research/building-effective-agents) post distinguishes fixed-path workflows from agents that dynamically choose their steps and tool use. It outlines composable patterns—prompt chaining, routing, parallelization, orchestrator-workers, and evaluator-optimizer—and notes the cost/latency trade-off of agentic complexity. The post itself warns that much of its tooling landscape has changed since its 2024 publication; treat the design patterns as historical guidance, not current product instructions.

For long-running coding work across context windows, Anthropic’s [long-running harness article](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) reports a two-role pattern: an initializer creates a runnable environment and structured feature list; later coding sessions select one incomplete feature, inspect progress and version history, test the baseline, implement incrementally, verify end-to-end, and leave the workspace and progress notes in a clean handoff state. The article is a particular research approach, not a requirement of the current Claude Code or Agent SDK.

The older [Claude Code best-practices post](https://www.anthropic.com/research/claude-code-best-practices) says it moved to the living docs on Jan. 26, 2026. Its repository, permissions, and command examples should be treated as historical; the current [best-practices guide](https://code.claude.com/docs/en/best-practices) is the maintained source.

## Instructions, skills, and memory

Current Claude Code guidance separates model-followed instructions from harness-enforced controls. Prompts, `CLAUDE.md`, and skills influence the model but do not guarantee compliance; hooks, deny rules, managed policy, tests, and CI can enforce deterministic behavior ([best practices](https://code.claude.com/docs/en/best-practices)). Use repository/user/org-scoped `CLAUDE.md` for concise, durable project knowledge; the current memory documentation also describes `AGENTS.md`, path-scoped rules, imports, and auto memory. These are context, not permission enforcement ([memory](https://code.claude.com/docs/en/memory)).

Skills package a name and description for discovery, on-demand instructions, and optional reference files/scripts. Anthropic’s API Skills documentation describes progressive disclosure: metadata is available up front, `SKILL.md` is read when a skill is relevant, and supplementary resources are loaded or executed only when needed ([Claude Code skills](https://code.claude.com/docs/en/skills), [API Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)). A separate 2025 [engineering article](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills) describes the same pattern and recommends deriving skills from observed task gaps, iterating on descriptions and content, and auditing trusted code/resources before installation. It notes Agent Skills became an open standard for portability; that historical announcement does not mean every Claude Code-specific frontmatter feature is portable.

The managed-agent skill guide adds host-specific discovery: mounted GitHub skill files are found once at session start at a specified `.claude/skills/<name>/SKILL.md` depth, rather than continuously searched. Anthropic's skill-authoring page recommends concise metadata and matching instruction rigidity to task fragility; this is authoring guidance, not a universal token budget. Managed Agents memory is a different mechanism: workspace-scoped text stores are mounted as files, may be shared across sessions, and create immutable versions on edits. The feature is beta and has a dedicated API/versioning contract; do not assume it is the same store as Claude Code auto memory or Messages API client-owned `/memories` files ([Managed Agents skills](https://platform.claude.com/docs/en/managed-agents/skills), [Skill best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [Managed Agents memory](https://platform.claude.com/docs/en/managed-agents/memory)).

## Tools, MCP, and context management

The Messages API tool protocol puts execution on one of two sides: client tools are executed by the application, while Anthropic server tools run on Anthropic infrastructure. Client tool results are returned in a subsequent request; server tools generally return results without requiring the application to run them ([tool-use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)). Claude Code can use local stdio or remote MCP servers; the current MCP reference recommends HTTP for remote servers, calls out deprecated SSE, and warns that external servers are a trust boundary ([MCP](https://code.claude.com/docs/en/mcp), [security](https://code.claude.com/docs/en/security)).

Managed Agents MCP integrations are configured differently: reusable agents reference a server, while credentials are supplied through a vault at session creation. The reviewed documentation says credential rotation can take effect in-session and that large tool outputs may be placed in a sandbox file with a preview returned to the model. A separate GitHub guide recommends minimum token permissions. These pages were partial reads; confirm current connector limits and lifecycle details before deployment ([Managed Agents MCP connector](https://platform.claude.com/docs/en/managed-agents/mcp-connector), [Managed Agents GitHub access](https://platform.claude.com/docs/en/managed-agents/github), [Vaults](https://platform.claude.com/docs/en/managed-agents/vaults)).

The current API tool-definition guide recommends precise schemas and descriptions explaining what a tool does, when it should and should not be used, parameter meaning, and limitations; examples help with nested or format-sensitive inputs. It also recommends namespacing across services, consolidating related actions when that reduces selection ambiguity, and returning compact, high-signal results. These are API tool-design recommendations, not guarantees that every host uses the same schema format ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).

Multiple `tool_use` blocks can arrive in one assistant response. The API does not prescribe whether the client executes them concurrently or sequentially: parallelize independent read-only work when safe, but serialize actions with shared state, side effects, or ordering constraints. Return a matching `tool_result` for every call together in the next user message, keyed by `tool_use_id`; if one was skipped after an earlier failure, return an error result for it. The exact batching/history rules are specific to this Messages API surface ([Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)).

The tool-combinations guide describes pairings such as search plus fetch, or text editing plus bash for coding. For client-executed code, a constrained working directory and command allowlist are necessary boundaries; the page recommends a browser tool instead of general computer use for web-only tasks. Programmatic tool calling can keep intermediate results inside a code-execution container rather than returning them all to the model, while the Bash tool's persistent shell lifecycle remains application-managed. These options change context and execution ownership, not the need to validate tool inputs and bound side effects ([Tool combinations](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-combinations), [Programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling), [Bash tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/bash-tool)).

Anthropic introduced MCP as an open protocol for clients to connect to servers that expose data and tools ([announcement](https://www.anthropic.com/news/model-context-protocol)). The [code-execution-with-MCP article](https://www.anthropic.com/research/code-execution-with-mcp) and [advanced-tool-use article](https://www.anthropic.com/research/advanced-tool-use) explore progressive discovery and orchestration in code: load only relevant tool definitions, process large/intermediate results outside model context, and return a focused result. The articles include reported token savings from particular experiments; these are not universal guarantees.

Context is not just the prompt. It includes instructions, tools, messages, tool results, and—depending on model and settings—thinking/output tokens. Anthropic’s current [context-window guide](https://platform.claude.com/docs/en/build-with-claude/context-windows) explicitly cautions that a larger window does not automatically make context more useful. The [context engineering article](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) recommends optimizing for the smallest high-signal context, using tools for just-in-time retrieval, and keeping tools distinct and well described. The API provides server-side context management features; the docs call compaction the primary strategy for most long-running conversations, with context editing for more specific clearing needs ([context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Current tool-search guidance adds an implementation pattern: defer less-used definitions, use structured descriptions/names to make retrieval work, and return compact results. The cited token savings and tool-count thresholds are vendor-reported and model/surface-specific, not universal constants.

The tool-context guide distinguishes prompt caching, tool search, context editing, and programmatic calling as different levers: cache stable prefixes, defer tool definitions when the tool list grows, edit accumulated history when needed, and keep intermediate tool computation out of model context where supported. Its recommended order and approximate tool-count threshold are specific guidance, not universal constants. The compaction overview describes on-demand compaction that can retain recent turns verbatim; threshold-triggered compaction has separate configuration. The reviewed docs use beta/version headers for these API features, so check live model and header support before relying on them ([Manage tool context](https://platform.claude.com/docs/en/agents-and-tools/tool-use/manage-tool-context), [Compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)).

The Agent SDK configuration surface adds operational limits and state caveats: `maxTurns` and budget limits can terminate a run with an error subtype; changing models mid-session can lose prompt-cache continuity. SDK observability is built on its CLI subprocess's OpenTelemetry output rather than SDK-owned telemetry, and prompt/tool contents are opt-in. File checkpointing only covers SDK-mediated file tools, not arbitrary shell edits or subagent changes, and rewinding files does not rewind the conversation. These features should be designed as separate recovery and observability layers, not one universal rollback mechanism ([Configuration](https://code.claude.com/docs/en/agent-sdk/configuration), [Observability](https://code.claude.com/docs/en/agent-sdk/observability), [File checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)).

Managed Agents has its own layered state model: a primary session stream summarizes work while per-thread streams expose subagent detail, and a session budget is shared across child threads. The reviewed guides describe multi-agent workflow runs that can fan out, pass results, retry, and pause on budget or interruption; unlike a pre-approved workflow definition, the agent can author a workflow dynamically. Beta token budgets span a tool loop and are not reset by compaction. Treat these as product-specific lifecycle rules and impose an explicit pre-execution review step when the task needs human approval ([Session threads](https://platform.claude.com/docs/en/managed-agents/session-threads), [Multiagent orchestration](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration), [Workflow runs](https://platform.claude.com/docs/en/managed-agents/workflow-runs), [Task budgets](https://platform.claude.com/docs/en/build-with-claude/task-budgets)).

Hosting is also a state boundary: SDK sessions use a long-lived local subprocess, and in-memory/session-local transcripts, memory files, and workspace artifacts are lost on restart unless persisted. Transcript stores do not automatically persist memory files. For multi-tenant hosts, isolate working directories and config, and review setting sources and auto-memory behavior explicitly ([Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)).

## Permissions, hooks, and safety boundaries

Claude Code’s permission rules are enforced by the harness. Its current docs distinguish permission modes, allow/ask/deny rules, working-directory boundaries, sandboxing, managed settings, and PreToolUse hooks; prompts and `CLAUDE.md` do not override those controls ([permissions](https://code.claude.com/docs/en/permissions), [security](https://code.claude.com/docs/en/security)). Hooks execute at defined lifecycle points and can inspect or block tool calls, react to results, and run at session/turn boundaries ([hooks reference](https://code.claude.com/docs/en/hooks)).

The SDK's permission guide describes an ordered evaluation across hooks, deny/ask rules, permission mode, allow rules, and `canUseTool`; a deny rule remains effective under bypass mode, but some bypass/auto-approved paths skip the callback. A PreToolUse hook matching only the built-in Write/Edit tools does not mediate shell commands that modify files. Use the actual tool boundary that can perform the side effect, and do not treat annotations or prompt text as enforcement. A custom system-prompt string can replace the default preset and its safety instructions, so custom prompts inherit that responsibility ([SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks), [Modifying system prompts](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)).

The current site documents auto mode as a permission mode using a classifier to evaluate some actions and reduce routine prompts; it is not equivalent to disabling permissions. Its boundaries and default behavior have changed over time, so consult the live [permission-mode](https://code.claude.com/docs/en/permission-modes) and [auto-mode configuration](https://code.claude.com/docs/en/auto-mode-config) docs. Anthropic’s [auto-mode engineering post](https://www.anthropic.com/research/claude-code-auto-mode) describes a layered design (input screening and action classification) and threat examples such as overreach, mistaken scope, prompt injection, and data exfiltration. Those implementation details are a dated product-engineering account, not a substitute for the current configuration reference.

The permission-mode matrix distinguishes Manual/default, `acceptEdits`, `plan`, `auto`, `dontAsk`, and `bypassPermissions`; the mode sets approval behavior but does not replace sandbox/isolation. The reviewed portion says deny rules still apply in every mode, including bypass, while exact starting defaults depend on product surface, configuration, and CLI version. The long page was only partially read, so this is not a full mode-by-mode security review ([Choose a permission mode](https://code.claude.com/docs/en/permission-modes)).

## Delegation and multi-agent work

Claude Code distinguishes focused **subagents**, which work in their own context and return findings to a parent session, from experimental **agent teams**, which are separate Claude Code instances coordinating through messages and shared tasks. The current agent-teams guide warns teams are experimental, disabled by default, cost more tokens, and work best when tasks are independent; it recommends subagents for simpler focused delegation ([subagents](https://code.claude.com/docs/en/sub-agents), [agent teams](https://code.claude.com/docs/en/agent-teams)).

Anthropic’s [multi-agent Research post](https://www.anthropic.com/research/multi-agent-research-system) describes an orchestrator/worker design for broad, parallelizable research: delegate bounded searches, use independent context windows as filters/compression, synthesize, and use a citation-focused pass. It also reports high token cost and warns that tightly coupled tasks are a poor fit. This is an example of a product architecture, not a general guarantee that multi-agent coding improves performance.

## Evaluation and quality loops

Anthropic’s agent-evaluation article defines task, trial, grader, transcript/trace, outcome, evaluation harness, agent harness, and evaluation suite. It stresses that the evaluated system is the model **and** harness together, and that an agent’s final message is not enough to establish success: verify the resulting environment state. It recommends combining code-based graders, calibrated model graders, and human review, using multiple trials for stochastic behavior, and distinguishing capability evals from regression evals ([Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)).

The API documentation similarly recommends explicit, measurable success criteria; representative tasks and edge cases; and automated grading where possible ([develop tests](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)). For coding agents, this points toward isolated and repeatable repositories/environments, end-state checks and tests, transcript/tool-use diagnostics, and tracking latency, cost, and reliability—not only whether the final prose sounds correct.
