# OpenAI coding-agent knowledge snapshot

**Snapshot:** 2026-11-18
**Scope:** Official OpenAI developer/API documentation, Codex and Agents material, selected official release records, and technical blog/research articles. This is an original synthesis, not a mirror of source prose. See [coverage.md](coverage.md) and [source-inventory.json](source-inventory.json) for the item-level catalog and limits.

## Executive synthesis

OpenAI's current materials describe coding agents as a model operating inside a larger **harness**: an execution loop, session/context management, tools, environment boundaries, approval handling, observability, and recovery. The product surfaces allocate those responsibilities differently. The Agents SDK runs its loop in an application the developer operates; the Agents API exposes a managed Codex harness and durable sessions; Responses API tools provide lower-level model/tool primitives for a developer-owned loop; Codex CLI/app-server offer an open-source coding-agent runtime and integration surface. These are related but not interchangeable. Start from the component that should own execution, state, and policy, and verify feature availability in that surface's current docs. ([Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk), [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview), [Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture), [Using tools](https://developers.openai.com/api/docs/guides/tools), [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform))

## 1. Harness and agent loop

The recurring loop is: prepare context and instructions; call the model; inspect its response; execute requested tools or transfer control; append results; repeat until a final result or a deliberate pause. One SDK `run` corresponds to one application-level turn, but may contain many model/tool iterations and specialist handoffs. Tool outputs are not merely presentation: they are new evidence for the next model step. Long tasks therefore depend on observable execution, explicit failure handling, and a way to continue the same task after interruption. ([Codex agent-loop article, 2026-01-23](https://openai.com/index/unrolling-the-codex-agent-loop/), [Agents SDK run loop](https://developers.openai.com/api/docs/guides/agents/running-agents), [Responses function calling](https://developers.openai.com/api/docs/guides/function-calling))

The **Agents API** makes the harness boundary explicit: an agent defines model, instructions, tools, and controls; a session persists a task and its state; an optional environment supplies compute and files; the application sends work and consumes events. With no environment, remote MCP and application-handled functions are possible, but built-in shell, workspace files, and executor MCP are not. OpenAI-hosted environments are managed by OpenAI; self-hosted environments put provisioning, reconnection, and lifecycle responsibility on the application. This separation is a useful architecture guide for a reusable coding harness: keep the loop/runtime, environment executor, product/application, and capability providers as explicit interfaces. ([Agents API concepts](https://developers.openai.com/api/docs/guides/agents-api/overview), [Architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture), [Quickstart](https://developers.openai.com/api/docs/guides/agents-api/quickstart))

Pre-warming is a setup lifecycle, not a way to restore session state: create an environment, wait for its ready signal, then attach it when creating a session. The guide documents webhook or polling readiness, but portions of its lifecycle/expiry and retry details were not reviewed in this snapshot ([Pre-warm sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/prewarmed)).

The current [Agents guide](https://developers.openai.com/api/docs/guides/agents) contrasts three execution owners: the hosted Agents API, an Agents SDK loop running inside the application, and direct Responses API calls with application-managed history/tool flow. ChatKit is another embedding surface, not a fourth interchangeable loop. Choose based on who should own session state, tool execution, approvals, and cleanup; an "agent session" in one surface is not the same resource as a Codex local thread, a Responses conversation, or a sandbox.

Workspace Agents is a separate organizational product surface: its reviewed docs describe scoped bearer tokens and triggering a published agent with an optional conversation key and idempotency key. Those pages label the capability beta. Do not copy its token, session, or trigger contract into Agents API or local Codex integrations. ([Workspace Agent authentication](https://developers.openai.com/workspace-agents/authentication), [Trigger a Workspace Agent run](https://developers.openai.com/workspace-agents/trigger-runs))

For multi-agent work, the documentation distinguishes **handoffs**, which transfer conversational ownership to a specialist, from **agents as tools**, where a manager keeps responsibility for the final answer. Add specialists only when their tools, policies, or output contract genuinely differ; otherwise the extra prompts, traces, and approval surfaces add cost without a clear benefit. Agents API subagents are intended for independent work, with each agent using its own context and the parent combining results. ([SDK orchestration patterns](https://developers.openai.com/api/docs/guides/agents/orchestration), [Agents API multi-agent](https://developers.openai.com/api/docs/guides/agents-api/multi-agent), [Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents))

Durability needs an explicit state strategy. The SDK documents replayable history, SDK sessions, Conversations API IDs, and Responses `previous_response_id`; mixing local replay with server-managed state can duplicate context. For Agents API work, events report live progress while items preserve messages/tool activity; webhooks can wake an application without holding an event stream open. Streams do not replay missed events, so retrieve the session/items and inspect the turn's terminal state after reconnecting; an idle session is not proof of success. Sessions and execution environments have separate lifecycles: an environment may disconnect or fail while the session remains usable, and reusing an environment ID does not restore its files. Save checkpoints and verify side effects before retrying because timed-out input is not automatically replayed. ([Running agents](https://developers.openai.com/api/docs/guides/agents/running-agents), [Events and items](https://developers.openai.com/api/docs/guides/agents-api/sessions/events), [Session webhooks](https://developers.openai.com/api/docs/guides/agents-api/sessions/webhooks), [Sessions](https://developers.openai.com/api/docs/guides/agents-api/sessions), [Environment lifecycle](https://developers.openai.com/api/docs/guides/agents-api/environments/lifecycle), [Errors and recovery](https://developers.openai.com/api/docs/guides/agents-api/errors))

Environment outputs are provider-dependent: the Agents API publishes selected OpenAI-hosted `/workspace/outputs` as immutable artifacts, while self-hosted output files must be retrieved through the application's environment provider. For self-hosted sandboxes, OpenAI runs the harness but the application owns compute startup, reconnect, teardown, isolation, and retrieval. Keep application credentials out of the sandbox; the docs describe restricted environment keys and separate vault-backed credentials. ([Files and artifacts](https://developers.openai.com/api/docs/guides/agents-api/environments/files), [Self-hosted environments](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted), [Vaults](https://developers.openai.com/api/docs/guides/agents-api/tools/vaults))

## 2. Context, instructions, and reusable capabilities

Current Codex documentation gives `AGENTS.md` a layered role. A run reads global guidance and then project instructions down to the working directory; more-local files arrive later in the concatenated instruction chain. `AGENTS.override.md` takes precedence in its directory, fallback names are opt-in, and combined instruction text is bounded (32 KiB by default in the current guide). That makes concise entry-point guidance plus navigable, versioned project documentation a better fit than one unbounded instruction dump. Treat these as product-documented discovery rules, not a universal convention across every OpenAI agent surface. ([Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md))

Skills package a reusable procedure in a directory with `SKILL.md`, required `name` and `description`, and optional references, scripts, and assets. Both the Codex product docs and API docs describe **progressive disclosure**: expose short metadata first and load detailed instructions when selected. The description is a routing signal, so state the target task and boundaries plainly; when a workflow has a strict contract, explicitly invoking it is more predictable than relying on implicit matching. In the Responses API, skills can be versioned and attached to hosted shell tools; Agents API sessions discover skills from environment directories. Avoid assuming that those attachment/discovery mechanisms are identical. ([Build skills](https://learn.chatgpt.com/docs/build-skills), [API Skills guide](https://developers.openai.com/api/docs/guides/tools-skills), [Skills + shell + compaction](https://developers.openai.com/blog/skills-shell-tips))

The plugins documentation makes the capability/workflow split explicit: an MCP server supplies live data, authentication, and actions; a skill describes the procedure for using such capabilities and can exist without an MCP server. ChatGPT workspace skills, local filesystem skills, and skills bundled in plugins have separate distribution and administration; moving a skill between them does not transfer sharing or installation state, and installing a plugin does not itself grant connector access. ([Plugin Skills](https://developers.openai.com/plugins/concepts/skills), [Skill controls](https://learn.chatgpt.com/docs/enterprise/skills))

Codex local `.rules` files are a separate, experimental execution-policy mechanism, not prompt instructions. The reviewed guide says matching `prefix_rule`s use the most restrictive decision, supports inline match/not-match tests, and applies local rules only to trusted project layers; Work Cloud uses different policy configuration. Simple linear shell chains can be evaluated command by command, while wrappers with control flow or expansion are opaque to that splitting. Test policy with the documented checker and do not assume local rules transfer to cloud execution. ([Codex Rules](https://learn.chatgpt.com/docs/agent-configuration/rules))

Codex's older local custom-prompt files are marked deprecated in favor of skills. The reviewed guide describes them as explicit slash-command templates under the user's local Codex prompt directory, not repository-shared or automatically applied guidance. This is a product-specific migration note: do not confuse interactive prompt templates with reusable skills or persistent instruction files. ([Custom Prompts](https://learn.chatgpt.com/docs/custom-prompts))

MCP is a connection protocol for tools and information, not an authorization boundary by itself. Responses API calls can connect to remote MCP servers; Agents API connections can originate from OpenAI's service or the task environment, and may use HTTP or environment-local stdio. The selected origin changes reachability, network policy, and credential handling. Minimize the tool surface, require explicit approval for sensitive actions where supported, and treat server responses and retrieved content as untrusted input. Never infer that a connected tool is safe simply because it is available. ([Responses API MCP guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp), [Agents API MCP connections](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp), [Codex MCP docs](https://learn.chatgpt.com/docs/extend/mcp))

An OpenAI engineering post describes Secure MCP Tunnel as an outbound-only customer-run connection for private MCP servers, with long-polling, backpressure, relayed events, and constraints on registered REST targets. Treat this as a design report, not a current deployment specification. The plugin tool-design guide separately recommends tools organized around user goals, split read/write actions and permissions, clear schemas and failure behavior, and accurate side-effect annotations; it explicitly cautions against returning unnecessary secrets or personal data. ([Private MCP servers engineering post](https://developers.openai.com/blog/connect-private-mcp-servers-to-openai-products), [Plugin tool design](https://developers.openai.com/plugins/plan/tools))

Agents API function tools execute in the application's code, not in the sandbox. A function call pauses the session for an application result; associate side effects with stable session/turn/call identifiers and persist results before returning them so reconnects do not duplicate work. Hosted computer use has a separate approval boundary: the reviewed guide requires approval for website origins and sign-in, but warns that origin approval does not confirm each purchase or other page action. Treat page content as untrusted and constrain resources independently. ([Functions](https://developers.openai.com/api/docs/guides/agents-api/tools/functions), [Computer use](https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use))

Context management is an operational concern, not a prompt-only concern. The current Responses guide describes server-side compaction as preserving selected prior state in an opaque compaction item and requires replaying output items in order; an alternative is explicit standalone compaction. Agents API changelog entries also document background compaction as a configurable behavior. Persistent local Codex memories are a separate feature, off by default in current docs; required rules belong in checked-in instructions rather than generated recall. Use artifacts, repository state, and short status/decision records as durable task state, while allowing the active model context to remain bounded. ([Compaction](https://developers.openai.com/api/docs/guides/compaction), [Codex memories](https://learn.chatgpt.com/docs/customization/memories), [API changelog](https://developers.openai.com/api/docs/changelog))

The Agents API exposes events/items, trace spans, and best-effort usage as separate observability layers. Usage may be absent or change and is not an invoice; traces become available after a turn and export requires organization-level enablement. Keep instructions and tool schemas stable where prompt caching matters, and do not assume truncated command output is explicitly signaled. ([Observability and usage](https://developers.openai.com/api/docs/guides/agents-api/observability), [Tracing](https://developers.openai.com/api/docs/guides/agents-api/tracing))

Long-running examples reinforce that context and memory solve different problems: a Cookbook walkthrough uses compaction to keep one review run viable and a human-reviewed memo as reusable workflow memory, while a separate improvement-loop example connects traces, human/model feedback, evaluation gates, and reviewable harness changes. These are illustrative, partial notebook reads—not product requirements or independent performance evidence. Codex "Goals" are another distinct completion contract, combining an outcome, verification criteria, and constraints for a resumable/budget-bounded task. ([Memory and compaction Cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction), [Agent improvement loop Cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop), [Codex Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex))

## 3. Permissions, isolation, and human control

The current Codex model separates two controls:

- **Sandbox:** technically bounds which files, processes, and network destinations commands can reach.
- **Approval policy:** determines when the agent must pause before crossing a boundary or performing a sensitive action.

Changing the reviewer does not enlarge the sandbox. Approval is not a substitute for OS-enforced isolation, and enabling network access is distinct from constraining it through a proxy or allowlist. Defaults and supported controls vary across local Codex, ChatGPT Work, Codex Cloud, and Agents API environments; validate the selected surface rather than copying a TOML or permission example across products. ([Sandbox](https://learn.chatgpt.com/docs/sandboxing), [Permissions](https://learn.chatgpt.com/docs/permission-modes), [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security))

For hosted and self-hosted agent environments, isolate workloads, restrict outbound traffic to necessary destinations, and keep application credentials outside agent-readable code. The Agents API docs distinguish application API keys from executor environment keys and recommend vault-backed secrets or a trusted proxy for third-party credentials. Automatic review can approve or deny supported permission requests, but it does not change network restrictions or replace the environment's sandbox. SDK-based applications must implement their own human review/guardrail behavior; Codex Auto-review does not automatically transfer to the SDK. ([Sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), [OpenAI-hosted sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/openai-hosted), [Automatic review](https://developers.openai.com/api/docs/guides/agents-api/sessions/approvals), [SDK guardrails and review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals))

The current safety guidance combines deterministic boundaries and review: guardrails validate input, output, or tool behavior; human review pauses a run before a side effect; resumable state lets the same run continue after a decision. Place checks at the boundary that can cause the side effect, and fail closed when a required reviewer or enforcement path is unavailable. Observability should record configuration, events, tool calls, approvals, and outcomes so operators can reconstruct what happened. ([Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals), [Persistent-agent security case study](https://developers.openai.com/blog/securing-persistent-agents-like-openclaw-at-openai))

Enterprise Codex security documentation distinguishes non-overridable global orchestration requirements from environment-specific sandbox, filesystem, and network settings; user defaults do not override enforced requirements. A separate safety guide recommends assuming model/tools or connected systems may be compromised, then containing risk with isolated disposable environments and independent filesystem, network, identity, and tool controls. These pages were partially reviewed, so consult their current complete policy references before configuring an environment. ([Agent Security](https://learn.chatgpt.com/docs/enterprise/agent-security), [Recommended security configuration](https://learn.chatgpt.com/docs/cyber-safety/recommended-configuration))

The Agent Builder safety guide adds a product-specific data-flow pattern: keep untrusted input out of privileged developer messages, constrain cross-node outputs with structured schemas, and require human approval for MCP operations. It also recommends input guardrails and trace grading while warning that these mitigations do not eliminate mistakes or prompt injection. Agent Builder itself is scheduled to shut down on **November 30, 2026**; preserve the design lessons, but do not start a new dependency on the retiring builder. ([Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety), [Agent Builder](https://developers.openai.com/api/docs/guides/agent-builder))

OpenAI's Windows sandbox engineering article describes an OS-level design that composes restricted tokens, dedicated sandbox identities, a command-runner process, filesystem ACLs, and firewall rules. It also recounts a weaker unelevated prototype whose environment-based network suppression was advisory and rejected as insufficient against bypass. This is a platform-specific case study rather than a portable sandbox recipe; the article itself emphasizes that its final setup requires elevation and is Windows-specific. The URL safety article describes a separate browser boundary: independently observed public URLs can be fetched automatically while unverified URLs require a safer path, but URL verification does not make destination content trustworthy or eliminate prompt injection. ([Windows sandbox engineering](https://openai.com/index/building-codex-windows-sandbox), [Agent link safety](https://openai.com/index/ai-agent-link-safety))

## 4. Evaluation and model choice

OpenAI's agent-evaluation guide recommends starting with traces to debug end-to-end decisions—tool choice, handoffs, instruction adherence, and safety—then moving to datasets and repeatable eval runs to compare changes. A practical coding-agent evaluation should separate **outcome** (did the requested change work?), **process** (did it use required tools/checks and honor constraints?), and **efficiency** (unnecessary retries, tool calls, or resource use). Keep deterministic checks for measurable properties and use rubric/human review for quality that cannot be reduced to a simple assertion. Skills can be evaluated as end-to-end workflows, including activation, required steps, and produced artifacts. ([Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals), [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Testing Agent Skills systematically](https://developers.openai.com/blog/eval-skills))

The Evals API reference page reviewed in this batch describes evaluation definitions and data sources, and marks `stored_completions` deprecated in favor of logs. It was only partially read, and a reference page is not evidence that the broader Evals platform remains available: the separate deprecations guide says that platform is read-only and scheduled to shut down. Recheck current product lifecycle before adopting any Evals endpoint ([Evals API reference](https://developers.openai.com/api/reference/resources/evals), [Deprecations](https://developers.openai.com/api/docs/deprecations)).

**Important dated platform change:** as documented in the November 18, 2026 snapshot, OpenAI's API docs say the Evals platform becomes read-only for existing users on **October 31, 2026** and is scheduled to shut down on **November 30, 2026**. The transition guidance points developers toward Datasets for iterative experimentation and retains trace-based evaluation as a separate surface. This affects the platform's Evals product, not the general practice of building application-owned tests or evals. Recheck the live deprecations page before implementing against any evaluation endpoint. ([Evals guide](https://developers.openai.com/api/docs/guides/evals), [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Deprecations](https://developers.openai.com/api/docs/deprecations))

Model recommendations in current docs are explicitly starting points: the API model-selection guide frames a set of models/reasoning levels against tasks, then recommends experimenting on representative inputs and keeping the lightest setting that meets a quality bar. The API changelog records GPT-6.2 Astra and Sol as released on **November 17, 2026**; the associated current guide describes tool-call compatibility constraints. Model names, availability, pricing, and product-specific feature support are volatile, so resolve them from the live catalog and dated changelog rather than older launch posts. ([Model selection](https://developers.openai.com/api/docs/guides/model-selection), [API model catalog](https://developers.openai.com/api/docs/models), [API changelog](https://developers.openai.com/api/docs/changelog))

## 6. Implications for the planned knowledge base and harness

For the repository's future coding-agent harness, the most reusable design lessons in this OpenAI material are:

1. Make model, loop, tools, execution environment, state, and product/application separately replaceable; choose deliberately which layer owns each.
2. Keep the active instruction surface short and navigable. Put stable project constraints in versioned files; reserve skills for task-triggered procedures and supporting assets.
3. Use durable state for the task (worktree/files, a plan/status record, logs and artifacts) and compact/recover conversational context rather than treating the prompt as the only memory.
4. Treat tools as capabilities with explicit schemas, scope, and failure semantics. Separate read from write operations; attach human review and deterministic policy at the side-effect boundary.
5. Evaluate the whole run, not only the final text. Capture traces and task artifacts, test both expected activation and non-activation, check process constraints, and grow the eval set from observed failures.
6. Version model/catalog and product capability claims with retrieval dates. Keep dated changelog facts distinct from current documentation and report stale or inaccessible source pages instead of silently substituting assumptions.

These are synthesized architecture implications, not OpenAI guarantees or a claim that one product surface implements every capability identically.
